# IRWS-R训练速度定位

日期：2026-10-24（Asia/Shanghai）。用户运行环境为Linux服务器、RTX5090 32GB，每台服务器6个训练程序；提供的命令指定CUDA_VISIBLE_DEVICES=0及--device cuda。当前本地不存在该服务器的IRWS-R正式训练记录，因此不能给出服务器真实的时间占比或并发减速倍数。

本轮只分析代码并在临时环境运行性能探针，没有修改算法、正式配置、Checkpoint或服务器进程。

## 结论

主要热点是细粒度串行网络更新及图嵌入反向传播；同卡6个进程会进一步争用GPU和CPU。显存容量足够仅说明能放下模型，并不表示每个进程获得独立算力。指定--device cuda已经使模型运行在GPU，不是命令遗漏CUDA。

S档5个模板平均27.6个任务；50工作流约1380次任务分配。batch=64是每区间抽样数量上限，当前仍逐样本执行四组Adam更新，不是64条样本合成一次梯度。若区间均不超过64条，一代约1380次样本更新、5520次优化器step，另有多次autograd.grad。

每条样本通过_sample重算所需完整DAG嵌入并重建最长16步历史；图网络按节点、双方向执行多次小GRU。每条样本更新Actor后，_outer_scores再对整个区间逐条前向、求两组外层梯度；若区间n条、抽样m条，该部分约m*n次Actor评估。

当前网络使用float64；大量float(tensor)、isfinite判断及数值诊断.cpu().numpy()使CPU与GPU频繁同步。游戏显卡的高FP32/Tensor算力不能直接转为这些小张量、FP64、串行任务的相同比例加速。原式逐样本更新增加了必要成本，但Python循环、重复常量构造和不必要同步不是论文要求。

## 本地测量

设备为Windows RTX4060Ti、PyTorch2.5.1+cu121、CPU线程1，cProfile会产生计时开销；输入采用真实S档DAX、临时固定归一化、无截止期缓存的占位deadline，仅测现有运算热点，不是正式S/S/Tight性能实验。CPU与CUDA分别采样，动作序列可能不同，不是严格相同轨迹的硬件加速比实验。

| 短程 | 训练耗时 | 无学习评估耗时 |
|---|---:|---:|
| CPU，2工作流，数值诊断开 | 8.48s | 0.24s |
| CUDA，2工作流，数值诊断开 | 5.93s | 0.21s |
| CUDA，2工作流，数值诊断关 | 5.51s | 0.16s |
| CUDA，5工作流，数值诊断开 | 16.36s | 0.48s |

CUDA五工作流共138次分配、138次样本更新、552次Adam step、966次反向引擎调用、66380次GRUCell调用（后两项来自仅训练阶段的cProfile）。update约13.64/16.36秒，占83%；反向约6.88秒，图编码前向约5.23秒；这些函数是嵌套关系，不能相加。仿真分配与时间推进合计远小于1秒。

本地二工作流关闭数值诊断由5.93秒变为5.51秒，一次短测约7%；说明诊断有开销，但单靠关日志无法消除主要网络计算成本。每代正式验证包含50工作流，确有额外成本；本次短程验证较快，不能据此认定服务器实际验证占比。1秒策略周期是虚拟仿真时间，程序没有按每个tick真实sleep一秒。

## 不改变现有算法语义的优化顺序

1. 下次受控运行先对比单卡1、2、6进程的每小时总episode，而不只看单个进程进度。可按CPU核数给各进程限制OMP/MKL线程，避免并发线程过量；该调整不改变学习超参数。
2. 将_outer_scores的区间Actor前向向量化，仍保留每条样本的四优化器更新顺序、每次更新后的Actor和完整区间求和。
3. 每区间一次准备冻结优势、old logp、cost、mask及观测张量；每个DAG只准备一次不可变拓扑。网络参数变化后仍须重算相关图激活，不能缓存旧嵌入而悄悄改变梯度。
4. 将只读诊断集中处理、减少GPU到CPU的往返；保留必要非有限值检查。
5. float32应另做数值对照，不能在“保持当前结果等价”的优化中静默替换float64。减少更新、改batch学习方式或减少验证频率会改变当前训练/选模协议，不应作为首选工程优化。

## 如何读取服务器已有阶段计时

在项目根目录执行以下只读脚本，可汇总每个IRWS-R运行的最近5个已完成回合：

```bash
python - <<'PY'
from pathlib import Path
import json
for p in Path('outputs/ckpts/irws_r').rglob('training_measurements.jsonl'):
    rows = [json.loads(s) for s in p.read_text().splitlines() if s.strip()][-5:]
    if not rows:
        continue
    print(p)
    print('episode=', rows[-1]['episode'])
    for key in ('train_seconds','validation_seconds','checkpoint_seconds','episode_wall_seconds'):
        print(key, round(sum(r[key] for r in rows)/len(rows), 2))
    print('last optimizer steps=', rows[-1]['optimizer_steps'])
PY
```

日志可区分训练、验证和保存，但无法独自衡量六进程争用的损失；争用比例需服务器受控对照。目前不对5090服务器承诺某一加速倍数。


## 与修改前irws_paper的直接对照

使用相同本地RTX4060Ti、CUDA、CPU线程1、诊断开启、相同S档DAX实例种子32及5工作流，分别运行当前两个实现。占位deadline和固定临时尺度仅用于热点分析，两个算法的策略、接口与日程本就不同；这不是服务器5090速度承诺或调度效果比较。两者都完成138次任务分配。

| 指标 | irws_paper | IRWS-R |
|---|---:|---:|
| 训练耗时 | 2.74s | 16.45s |
| 每个优化器的更新次数 | 3 | 138 |
| 四优化器step合计 | 12 | 552 |
| 反向引擎调用 | 12 | 966 |
| 图编码调用 | 24 | 297 |
| GRUCell调用 | 5492 | 66380 |
| 无学习评估耗时 | 0.59s | 0.48s |

本次单进程短测IRWS-R训练约慢6.01倍。更新次数放大不等于耗时必然同比放大；旧版本单次批次计算更大，故不能称总体慢46或64倍。

### 明确新增的拖慢来源

1. 旧版攒满64条或episode结束，调用一次losses并让每个优化器step一次；当前每区间抽样后，对每个样本分别执行四个step。该短测旧版[64,64,10]共3轮；新版138轮样本更新。此项来自恢复Algorithm 1逐样本循环，确实改变了训练计算预算。
2. 旧版每批统一编码所需DAG一次；当前每个_sample重算DAG，参数每样本又会改变，单纯沿用旧嵌入会改变梯度。可缓存不可变拓扑、减少常量构造、向量化同层计算，但不能跨参数更新无条件缓存图激活。
3. 旧版每批一次虚拟内步及外层代理求导；当前每条样本实际更新Actor后，_outer_scores对全区间再次逐条前向并求两组梯度。旧版原本也有高阶元梯度，主要差异是频率和范围，不是从无元梯度变成有元梯度。
4. 旧版批内按时序扫描RNN一次；当前每个抽样点重建最长16步前缀，该短测更新阶段RNN历史步骤由138变为506。该实现确保时序，却引入重叠前缀的重复计算。
5. 区间更新替代固定64条更新后，编码缓存清空更频繁；另增加边界refresh，该短测额外50次。队列本身的入队、出队和物理推进并非主要热点。
6. 梯度诊断、有限性判断、标量回传也随逐样本更新次数一起增加。诊断机制原来已经有，新增的是执行频率。

### 不能当作此次变慢原因的项目

float64、相同图网络的逐节点GRU、主要隐层宽度、每代验证及模型保存，在irws_paper原本就存在。删除熵、删除联合任务概率、冻结Q、删去三项观测及RNN两个额外字段均减少计算或影响很小。融合公式算术和irws_r身份/文件改名没有足够成本解释数量级退化。六进程并发会放大细粒度计算竞争，但单进程对照已经存在明显版本速度差。

优先优化目标应是上述新增重复计算；若直接恢复旧64条联合更新，能够减少工作量，却会重新偏离本次明确恢复的逐样本学习过程，不应在声称算法等价时悄悄这样修改。
