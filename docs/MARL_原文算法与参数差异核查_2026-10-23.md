> 这是改造前实现的历史核查。2026-10-23后续已按用户方案切换正式MARL入口，当前实现见 [MARL Q适配说明](MARL_Q_implementation.md)。下文代码行号与结论描述的是改造前状态。

核查日期：2026-10-23（Asia/Shanghai）。Git HEAD：`c3dd80586f5372123090cb6728ce8c3866abbca3`。对象为当前工作区 `algorithms/marl/train.py`、`evaluate.py` 实际调用的 `agents.py`、`environments/marl.py`，以及公共轨迹、归一化、资源、工作流和实验协议模块。没有修改算法、参数、模型或已有实验结果。

**结论：有明确偏离，也有原文未描述、可能帮助训练的附加设计。当前实现应称为“采用参数共享 A2C 的两级云工作流适配版”，不能称为原论文 MARL 的严格复现。最重要的问题是原文的邻域集中式 Q Critic 没有实现，此外还改写了策略共享方式、观测、奖励和 Local 价值衔接。**

这里的“可能增强”表示有明确的信息、探索、数值稳定或样本复用机制，不表示已经通过实验确认收益。部分偏离也可能降低性能；没有进行消融，不能把当前 MARL 的性能归因于某一项。

## 2. 明确的算法机制偏离

### 2.1 原文核心的邻域集中式 Q Critic 被状态价值 A2C 替代

原文 p.609 式(12)使用带联合动作输入的 Q 函数，图 3 与 p.610 正文将共享范围限制到局部邻域：Local 的 Q 使用自己的观测和动作；Global 的 Q 使用自己的观测/动作及本次被选中 Local 的动作。Algorithm 1 第 7–9 行接收 Local 的奖励与动作，并组合 Global/Local 动作。

当前 `algorithms/marl/agents.py:121–125` 的 Global 网络仅执行 `forward(obs)`，输出 `logits` 和 `V(obs)`。`algorithms/marl/train.py:313–315` 的 Global 更新只传入 Global 观测、Host 动作、Global 奖励及下一 Global 观测，没有传入本次 `a_vm`。Local 网络同样用 `V(local_obs, host_index)`，没有把 Local 动作作为 Critic 输入。

当前学习实际为：

```text
y = r + 0.95 * (1-done) * V(next_obs)
advantage = stop_gradient(y - V(obs))
loss = -log pi(action|obs) * advantage
       + 0.5 * MSE(V(obs), y) - 0.01 * entropy(pi)
```

证据：Global `agents.py:189–199`；Local `agents.py:371–385`。

这改变了原论文的核心多智能体协作机制，不能仅以“都有两级 Actor-Critic”判定一致。举例，在相同 Global 观测下，Local 选择不同 VM，原文的 Global Q 可以以不同 Local 动作为条件；当前的 `V(global_obs)` 无法直接以这些动作区分价值。收到受 Local 动作影响的标量奖励，并不等于实现了该 Critic 输入机制。

复现处置：若保留当前实现，应披露其为状态价值 A2C 适配；若恢复原法，应先恢复 Global/Local 的 Q 输入与邻域协作路径，不能仅关闭熵或缩小网络。

### 2.2 Local 引入共享策略和 Host 身份输入；Critic 只有最后一层独立

原文 p.609 图 3 为各 Local 绘出各自 Actor/Critic；式(12)以各 agent 的参数 `theta_i` 表述策略，并说明 Q 函数分别学习。原文没有描述当前的参数共享方案。

当前 `agents.py:268–276`：

- 所有 Host 共用一套五层 `backbone`。
- 所有 Host 共用一个 `policy_head`。
- 每 Host 只有一个独立的线性 `value_head`，输入仍来自共享 backbone。

训练入口 `train.py:220–222` 实际实例化了这个类。`environments/marl.py:1229–1233` 额外拼接 Host one-hot，供共享策略识别主机。

这是可实质影响学习的额外结构设计：一个 Host 的样本会更新其他 Host 也使用的策略和特征网络，有机会改善样本利用率；one-hot 则允许同一策略学习主机特有的行为。也可能产生负迁移，收益方向需要实测。代码类名里的 IndependentCritic 只能理解为输出头独立，不能描述为每 Host 完整独立的 Critic 网络。

复现处置：论文与实验说明应准确披露“共享 Actor/特征干线、Host 专属价值头及 Host one-hot”；严格复现不能未经说明套用该共享结构。

### 2.3 Local 经验跨 Host 衔接，改变了原文每个 Local 的决策轨迹

原文 p.610 Algorithm 2 按每个 Local scheduler 接到的任务序列更新，正文还说明其他 Local 的动作/观测不影响该 Local 的后继观测。

当前 `train.py:285,303,316` 每回合只维护一个 `LocalDecisionTrace`。`common/f11.py:118–121,170–175` 将任意下一次实际 Local 决策作为上一条经验的后继；`agents.py:372–377` 使用下一 Host 的价值头：

```text
y_local = r_local + gamma * V_next_host(next_local_obs)
```

例如调度顺序为 Host A → Host B，A 的经验目标中会含有 B 的未来价值，并非等待 A 自己下一次接到任务再衔接。

`docs/revision_F11.md:68` 已明确记录：这是条件化 Local 联合决策轨迹，不能宣称原论文已明确规定。它是额外学习定义，效果可能正负皆有，不能作为已证实的增强。

复现处置：保留时需明确其学习目标；恢复每 Local 的原文结构时，应一并明确每 Host 的状态后继、奖励累计和终止规则，不能只删除 `next_host_index`。

## 3. 状态与奖励的实质重写

### 3.1 增加截止期与执行预测特征，同时删除原 Global 的重要区分信息

| 层级 | 原文 pp.610–611 | 当前实际输入 |
|---|---|---|
| Global | 每个 DC 的绿色能源盈亏、平均服务器速度、利用率数组；当前任务 CPU/内存要求 | 固定 10 维全局队列与负载聚合，包括 Ready/Blocked/Running 比例、等待均值/最大值、空闲 VM 比例、主机负载均值、工作流 Slack 最小值/均值 |
| Local | 每个服务器速度、利用率；当前任务 CPU/内存要求 | `12 + 10 + 5 + 5*maxVM + H` 维，包括任务 MI、输入/输出量、I/O ratio、等待时间、best/mean 预计执行时长、Slack、同工作流 Ready 占比、全局队列紧急度、Host 特征、各 VM 带宽和预计完成时长、Host one-hot |

证据：`environments/marl.py:170–187,990–1068,1070–1234`。当前 Global 没有原文按 DC 排列的差异数组，也没有当前任务的独立特征块；动作合法性 mask 仍透露各 Host 是否有空闲 VM，不能说完全没有 Host 信息。

新增的预计执行时长、VM 预计完成、Slack 和紧急任务占比，有机会帮助策略直接感知执行代价和截止期风险，属于手工特征工程。与此同时，Global 的聚合会损失信息：当两个 Host 的负载互换、聚合量与 mask 相同时，Global 观测可能不变，不能像原文的逐 DC 数组那样定位负载属于哪台主机。因此，状态重写包含潜在增强与潜在弱化，不能一概称为“更强状态”。

预测时长由已知任务属性、资源和已完成父任务位置计算（`marl.py:940–950`），未发现使用未来真实完成时间或测试标签。

### 3.2 时间—能耗/绿色能源目标被任务迟交—主机窗口能耗替代

原文 p.610 式(14)的 Global 奖励包含所选 DC 的绿色能源盈亏与 Local 奖励。p.611 式(16)的 Local 奖励结合任务执行时间与任务能耗；pp.606–607 的系统目标包含 brown energy，式(6)的任务时间含计算、等待及父任务传输。

当前默认 `train.py:160–162` 设置 `energy_reward_scale=0.001`、`task_baseline_norm=300`、`alpha_delay=0.75`。`environments/marl.py:372–385,698–721` 实际使用：

```text
d = min(1, max(0, task_finish - task_LF_subdeadline) / 300)
r_global = -0.75*d - 0.25*0.001*delta_system_host_window_energy
r_local  = -0.75*d - 0.25*0.001*delta_selected_host_window_energy
```

明确差异：

1. 加入原方法没有的任务 LF 子截止期及迟交反馈。
2. 两个都不迟交的动作，其时间奖励均为 0；迟交超过 300 秒后，延迟惩罚饱和。原文目标是任务执行时间与能耗，并非这个分段迟交函数。
3. Global 不再读取绿色能源盈亏，也不按原式(14)组合 Local 奖励；Global 与 Local 的能耗范围分别是全系统与所选 Host。
4. 能耗在事件推进区间结算，连续同一时刻分配可能先收到 0 能耗反馈；它不是对每个任务单独按原式(7)–(9)计算能耗。

该奖励更直接面向当前截止期和主机能耗评价，存在改善这些指标的可能，但它首先是目标替换。不能仅称为将原文 alpha 改成 0.75。

原文自身有两处表达歧义：式(16)将正的时间/能耗成本写作 reward，而前文目标为最小化；Algorithm 1 的奖励加法与式(14)中 Local 奖励的位置也不完全一致。因此本核查不把负号或 Local 奖励应精确累计几次单独判为增强，也不建议未经澄清机械照抄这些符号。

### 5.2 没有发现启用的增强

- 任务按 ReadyTime、任务 ID 的 FCFS 顺序选择（`marl.py:600–610`）。未加入 HEFT、EDF、Rank 排序器或学习式任务排序器。虽然计算了上下行 Rank，Local 任务块对应三项仍为 0（`:1155`）。
- 未发现 MARL 训练路径启用 PER、经验回放、Double/Dueling、目标网络、PPO、GAE、优势标准化、图网络、专家引导、能耗候选重排或启发式后处理。
- 原文明确使用 TD 和逐步更新，所以不能把“一步 TD”本身列为额外增强。原文也没有规定必须采用 replay/target network，不能仅因引用 Lowe 等人的论文就把它们未实现算作遗漏。
- `agents.py` 中的 `load_weights_flexible()` 支持跨维度剪裁复制，但正式评测 `evaluate.py:169,171` 使用严格加载，不调用该函数。它不属于当前默认评测收益来源。
- F11/F19 数值诊断为记录功能；已有测试检查开关诊断不改变更新后的参数，不能将其本身计作训练增强。

直接回答本次问题：

1. **是否偏离原文：是。** 核心 Q 协作机制、Local 策略结构/轨迹、状态和奖励均有变化。
2. **是否增加原文未描述、可能增强性能的设计：是。** 优先关注参数共享 + Host one-hot、截止期/预计执行特征、熵正则、梯度裁剪和训练参考尺度预处理；其中公共归一化不能称为 MARL 独享优势。
3. **是否已经证明更强：没有。** Global 信息聚合、核心协作缺失与跨 Host 价值耦合也可能带来负面影响。
4. **论文中如何描述：** 建议明确标为“基于该工作两级框架的参数共享 A2C 适配基线”，披露改变，避免“原文算法和参数完全一致”。若需要严格复现，应先恢复邻域 Q Critic 与每 Local 的学习定义，再讨论哪些公共问题适配可以保留。
5. **如何验证增强来源：** 在同一公共物理环境、奖励、数据划分与训练预算下，分别比较共享/独立 Local、增加/移除 Host ID、增加/移除预测和截止期特征、熵与裁剪开关。公共归一化的影响应对全部比较算法一起控制；不要一次删除所有组件后就把差值归因于某一项。
